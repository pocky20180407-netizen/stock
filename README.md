# 台股模擬交易 APP — 專案說明

這份文件記錄整個專案的架構與進度，之後每次有新進展都會更新。

## 整體架構
- **資料來源**：證交所（上市）＋ 櫃買中心（上櫃）官方公開資料，全部免費，涵蓋全部台股
- **後端**：Cloudflare Workers（排程抓資料、跑選股邏輯、模擬交易）＋ Cloudflare D1（資料庫）
- **前端**：PWA 網頁應用，用 Capacitor 包裝成 Android 安裝包（內建原生 AdMob 廣告），上架 Google Play；用 GitHub Actions 免費自動化建置
- **費用**：全部使用免費額度；上架 Google Play 只需要你已經有的開發者帳號，AdMob 帳號免費申請，沒有其他費用

## 重要決定：為什麼打包方式從 TWA 改成 Capacitor
一開始規劃的是用 Bubblewrap／PWABuilder 把 PWA 包成 TWA（Trusted Web Activity），這是最簡單的免費上架方式。但你提出要加 Google AdMob 廣告後我查證過：**TWA 目前沒有官方支援的方式可以顯示原生 AdMod 廣告**——這不是我的猜測，是 Google 自己維護 TWA 工具的 GitHub 上，開發者明確回覆「TWA 全螢幕交給 Chrome 渲染，沒辦法疊加原生的 AdView」，這個功能請求目前還沒有解法。

改用 **Capacitor** 解決這個問題：一樣是把同一份網頁程式包成 Android APP，但 Capacitor 有能力橋接原生功能，官方文件直接推薦搭配 `@capacitor-community/admob`（積極維護中）來加廣告，支援橫幅、插頁、獎勵廣告，還內建歐盟GDPR同意聲明的處理。

**這個改變唯一的取捨**：Capacitor 版本會把網頁介面「打包」進安裝包裡（不像原本 TWA 那樣即時讀取線上網頁），所以之後想改「介面／版面」需要重新打包上傳到 Google Play（跟一般APP更新一樣）。但**股價、選股結果、虛擬帳戶績效這些「資料」完全不受影響**，一樣是每次都即時向後端 API 拿最新資料——只有「畫面長相」需要透過更新發佈，這是所有原生APP的正常運作方式。
- 已完成的後端程式（indicators.js、conditions.js、資料抓取、交易引擎）完全不受這個改變影響，不需要重寫。

## 已完成：Phase 1（核心運算邏輯）
- `backend/src/indicators.js`：技術指標計算引擎
  - SMA 均線、KD（9,3,3）、RSI（14日）、布林通道、量比
  - `buildIndicatorBundle()`：一次算好一檔股票所有常用指標
- `backend/src/conditions.js`：選股條件庫＋策略判斷引擎，目前有13種條件類型：
  - 技術面：KD黃金／死亡交叉、站上／跌破均線、RSI超買／超賣、成交量爆量、突破布林上軌
  - 籌碼面：三大法人連續買超
  - 基本面：本益比低於、殖利率高於
  - 出場：停利百分比、停損百分比
  - 每個策略可以自由組合多個條件，設定「全部符合」或「符合任一」
- `backend/schema.sql`：資料庫結構（股票、歷史股價、策略、虛擬帳戶、持倉、交易紀錄、每月績效）
- `backend/test-sanity.mjs`：已執行測試，確認指標數值範圍正確、選股邏輯判斷正確（全數通過）

這些是「地基」部分，先做這裡是因為不管其他細節怎麼微調，這部分都不會變。

## 目前的模擬交易規則（預設值，可調整）
- 每個虛擬帳戶起始資金：新台幣 100 萬
- 每次觸發買進訊號，固定投入 10 萬元整（不足一張零股不買），最多同時持有 10 檔
- 同一檔股票、同一策略，沒出清前不重複買進
- 賣出：觸發賣出條件時全部出清
- 交易成本：手續費 0.1425%（買賣都算）、賣出另計證交稅 0.3%
- 勝率＝已出清交易中賺錢的筆數 ÷ 總出清筆數；每月同時比較勝率、總報酬率、最大回撤

- `backend/test-data-parsing.mjs`：用真實欄位格式模擬測試過解析邏輯，全數通過

**模擬交易引擎已完成並測試：**
- `backend/src/trading.js`：`executeBuy()` / `executeSell()`，實作資金配置、手續費（含最低20元）、證交稅計算
- `backend/test-d1-adapter.mjs`：用 Node 內建的 node:sqlite 包出跟 Cloudflare D1 一樣的介面，讓測試能跑「真的 SQL」
- `backend/test-trading.mjs`：用真實資料庫跑過完整流程（買進、防重複買進、資金不足、檔數上限、賣出算損益），全數通過
- **測試中發現一個真實的小細節**：起始資金剛好是「10檔 × 10萬」時，因為每筆交易還要付手續費，實際上通常只能買到 9 檔，買不滿 10 檔——這跟真實券商帳戶的情況一樣，不是bug，先讓你知道這個自然的限制存在。

**還沒做的部分：**

- 三大法人買賣超資料的串接（INSTITUTIONAL_BUY_STREAK 條件目前還沒有真正的資料來源）
- 排程主程式：交易時段內每 5 分鐘執行一次「抓資料 → 跑 10 組策略 → 模擬買賣 → 寫入資料庫」，把上面已經做好的各個模組串在一起

## 重要決定：上櫃資料為什麼改用 GitHub Actions 中繼
實際部署測試時發現，TPEx（櫃買中心）的伺服器會擋掉從 Cloudflare Worker 發出的請求（回傳 HTTP 520），查證後這是已知的常見狀況——不少公開服務會把 Cloudflare／AWS／GCP 這類雲端服務商的IP當成機器人擋掉，不是我們的程式碼寫錯，加強瀏覽器標頭也沒用（因為擋的是IP本身）。

解法：改用 **GitHub Actions**（不同的網路來源）獨立抓取上櫃資料，透過一個新增的 `/ingest/otc` 端點推送進同一個資料庫；Cloudflare Worker 的主流程改成直接讀資料庫裡的上櫃資料，不再自己去抓。上市（TSE）資料維持原樣，由 Worker 直接抓取（已確認1366檔全部正常）。這個改變完全不影響選股、模擬交易的核心邏輯。

- `.github/workflows/fetch-otc.yml`：GitHub Actions 排程設定，時間跟 Cloudflare 的 cron 對齊
- `scripts/fetch-and-push-otc.mjs`：實際執行抓取＋推送的腳本，直接複用 `backend/src/data/tpex.js` 裡已經測試過的解析邏輯
- `backend/src/index.js` 新增 `/ingest/otc` 端點，用一組密語（secret）驗證，避免被亂寫入資料
